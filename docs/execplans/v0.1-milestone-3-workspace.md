## Purpose and observable outcome

After this milestone, a trusted local owner process can:

- initialize a project store from a validated ProjectIR and safety context;
- fork independent agent workspaces;
- apply edit batches to a workspace with revision checks and deduplication;
- undo and redo exactly, and replay history to prove determinism;
- store per-workspace free-form notes (storage only, for the Proposal 001 notes tool);
- discard, freeze a research submission, or promote a workspace to accepted state.

None of these operations can corrupt accepted state or another workspace.

Every state change goes through the Milestone 2 kernel. No caller, including a model, can write project state, restore arbitrary IR, or bypass locks.

This is the reversibility layer that the AGENTS.md rule ("every state-changing kernel operation must be reversible") depends on.

## Storage layout

This is a subset of the parent plan's layout. Asset and artifact directories arrive in M4.

```text
<storeRoot>/                         # caller-supplied; default .aether (already gitignored)
  projects/<projectId>/
    owner.lock                       # single-writer guard (D4)
    snapshots/<contentHash>.json     # canonical ProjectIR, immutable
    safety.json                      # KernelSafetyContext, immutable after init
    accepted-head.json               # AcceptedHead, atomically replaced: the project commit point
    workspaces/<workspaceId>/
      task.json                      # TaskInstructions, immutable after fork
      head.json                      # WorkspaceHead, atomically replaced: the workspace commit point
      receipts/<receiptId>.json      # immutable batch receipts; receiptId is hash-derived
      notes.json                     # { revision, text }, atomically replaced
      attempts.jsonl                 # append-only mechanical trace; never consulted for state
```

The store never constructs or reads any `evaluations/` path.

**Commit-point rule.**
- Each workspace has exactly one commit point, its `head.json`. The project has exactly one, `accepted-head.json`.
- A snapshot or receipt counts as committed **only if a commit point references it**.
- Files that no commit point references are orphans. They are ignored for every purpose, including deduplication.
- Agent-supplied `batchId`s are never used as path components; they live only inside `head.json`.

## Contracts (Zod, in `@aether/workspace`)

**`StoreSegmentSchema`.** Applies only to `projectId` and `workspaceId`, the only caller-chosen IDs used as directory names (D3).
- Regex `^[a-z0-9](?:[a-z0-9-]{0,62}[a-z0-9])?$`. Lowercase only, so case collisions are impossible. No dots, so there are no trailing-dot or extension aliases.
- Windows reserved device names are rejected in addition: `con`, `prn`, `aux`, `nul`, `com1`–`com9`, `lpt1`–`lpt9`.
- Core `IdSchema` is broader than this, so these IDs are validated separately before any filesystem access.

**`WorkspaceHeadSchema`.** Reuses and extends the existing `AgentWorkspaceSchema`:
- `{ schemaVersion: 1, id, projectId, base: SnapshotRef, head: SnapshotRef, safetyContextHash, taskId, state: 'open' | 'frozen' | 'committed' | 'discarded', undoReceiptIds, redoReceiptIds, committedBatches, submission? }`
- `committedBatches: { batchId, payloadDigest, receiptId }[]` is append-only and is the **only** deduplication index. It includes no-change batches.
- `submission?: { revision, contentHash, notesRevision }` is present exactly when `state === 'frozen'`.
- The existing `proposedBatches` and `previewIds` fields are kept empty in M3 (previews arrive in M4).
- Adding `'frozen'`, `committedBatches` and `submission` is a schema change (D2).

**`AcceptedHeadSchema`.** `{ schemaVersion: 1, revision, contentHash, promotions: { revision, workspaceId, workspaceRevision }[] }`. `promotions` is append-only and is the authoritative record that a workspace was promoted.

**`BatchReceiptSchema`.**
```text
{
  schemaVersion: 1, receiptId, workspaceId, batchId, payloadDigest,
  fromRevision, toRevision,
  beforeContentHash, afterContentHash, safetyContextHash,
  operationReceipts, clipMappings, changed
}
```
- `receiptId = "receipt-" + sha256(canonicalSerialize({ domain: 'aether.receipt.v1', workspaceId, batchId, payloadDigest }))`.
- `payloadDigest = sha256(canonicalSerialize(requested EditBatch))`.
- No timestamps or latency fields; those go only in `attempts.jsonl`.

**`AttemptRecordSchema`** (one JSON line per attempt):
- `{ sequence, kind: 'edit' | 'undo' | 'redo' | 'promote' | 'discard' | 'freeze' | 'notes', outcome, errorCode?, receiptId?, elapsedMs }`
- Mechanical data only: no batch payload text beyond IDs, and nothing from hidden inputs.

**`WorkspaceError`.** A typed union, separate from `KernelError`:
- `stale_revision`, `workspace_mismatch`, `workspace_not_open`, `batch_id_conflict`
- `stale_base`, `safety_changed`, `store_corrupt`, `owner_locked`
- `nothing_to_undo`, `nothing_to_redo`, `notes_too_large`, `invalid_segment`
- `kernel` (wraps the unchanged `KernelError`)

Errors carry only public mechanical evidence, following Milestone 2's rule.

## Operations and exact semantics

All mutating operations below require an open owner session (D4). Each mutation follows the same publish protocol:

1. Validate inputs.
2. Compute the result in memory.
3. Write new immutable files (snapshot if absent, receipt) using temp-file-then-rename.
4. **Commit:** atomically replace exactly one commit-point file.
5. Append the attempt line. This is best-effort trace data, never consulted for state.

If the process stops before step 4, the old commit point stays valid and any new immutable files are orphans, ignored for every purpose. Because deduplication reads only `head.json`, a retry after such a crash applies the batch fresh; it never reports a false success.

### `initProject(storeRoot, project, safety)`
- Validate `project` with `ProjectIRSchema` and `safety` with `KernelSafetyContextSchema`.
- Require `safety.projectId === project.id`.
- Run the D1 state check.
- Write the snapshot, `safety.json` and accepted head `{ revision: 0, contentHash }`.
- Fails if the project already exists.

### `forkWorkspace(projectId, workspaceId, task)`
- Validate `task` with `TaskInstructionsSchema`.
- Create a head where `base = head = accepted head`, bound to the hash of `safety.json`, with state `open` and empty stacks.
- Fails on an existing or case-colliding ID.

### `applyEditBatch(projectId, batch)`
1. Parse the `EditBatch`.
2. Validate the segment IDs.
3. Load the workspace from `batch.workspaceId` and require state `open`.
4. Require that `safety.json` still matches the bound hash, otherwise `safety_changed`.
5. **Deduplication (reads `head.committedBatches` only):** if `batchId` is present:
   - same `payloadDigest`: return the original stored receipt with `replayed: true` **and the current head `{ revision, contentHash }`**. This follows the parent plan's "refresh the head after historical results". It matters when the batch has since been undone. There is no state change, apart from an attempt line.
   - different digest: `batch_id_conflict`.
6. Require `batch.expectedRevision === head.revision`, otherwise `stale_revision` with no change.
7. Load the head snapshot (D5 verification) and call `executeEditBatch(project, batch, safety)`.
8. On kernel failure: record the attempt and return a `kernel` error. Head, history and files are unchanged.
9. On success with `changed: true`:
   - write the snapshot and receipt;
   - commit a new head with `{ revision: head.revision + 1, contentHash: after }`;
   - push the receipt onto the undo stack;
   - **clear the redo stack**;
   - append to `committedBatches`.
10. On success with `changed: false`:
    - write the receipt (`fromRevision === toRevision`);
    - commit a head that differs only by the appended `committedBatches` entry, so retries stay idempotent;
    - the revision, content and stacks are unchanged, so the batch is not undoable;
    - return a documented `no_change` result. This matches the parent plan's "no-change result rather than an applied-edit receipt".

### `undo(projectId, workspaceId, expectedRevision)`
- Require state `open` and a matching revision.
- Pop the last undo receipt, load its `beforeContentHash` snapshot through D5 verification, and set the head to `{ revision + 1, beforeContentHash }`.
- Push the receipt onto the redo stack.
- The restored content comes only from a stored, hash-verified snapshot, never from caller input.

### `redo(...)`
The mirror of `undo`, using `afterContentHash`.

### Revision rule
Revisions increase monotonically on every head change. Content hashes may repeat, so undo restores the exact content at a new revision.

### `replay(projectId, workspaceId)`
- From the `base` snapshot, re-apply the **effective** operations of each receipt currently on the undo stack, in order, using `applyBatch`.
- Assert that each result's `afterContentHash` equals the stored receipt and that the final hash equals the head.
- Returns a report: `{ ok, checkedReceipts, firstMismatch? }`.
- Read-only.

### `writeNotes(projectId, workspaceId, expectedNotesRevision, text)` / `readNotes(...)`
- Notes are untyped UTF-8 text, bounded (D6: 16 KiB).
- They have their own revision counter. They never touch ProjectIR, content hashes, the workspace revision or the undo stack.
- Allowed only while state is `open`. The text is stored verbatim, and the kernel and compiler never parse it.

### `discard(projectId, workspaceId)`
Sets state to `discarded`. All later mutations fail with `workspace_not_open`. Files are retained for research traces.

### `freezeSubmission(projectId, workspaceId)`
- Commit a head with `state: 'frozen'` and `submission: { revision, contentHash, notesRevision }`, in one atomic write to the single commit point. There is no separate submission file.
- The workspace becomes read-only.
- This does not require promotion or editorial success, and it never consults hidden data. This is the parent plan's "research submission freezes the designated workspace".

### `promote(projectId, workspaceId, expectedAcceptedRevision)`
Preconditions:
- effective state `open` (see below);
- accepted head equals `workspace.base` and `expectedAcceptedRevision`, otherwise `stale_base` (no auto-merge);
- the D1 state check passes against `safety.json`;
- the head timeline has at least one clip ("non-empty renderability"; real render checks arrive in M4).

Then:
1. **Commit:** atomically replace `accepted-head.json` with `{ revision + 1, contentHash: workspace head }`, appending `{ revision + 1, workspaceId, workspaceRevision }` to `promotions`.
2. **Best-effort follow-up:** set the workspace head's `state` to `committed`.

**Effective workspace state.** A workspace listed in `accepted-head.promotions` is `committed`, whatever its own head says. A crash between steps 1 and 2 therefore still leaves a consistent store. The next load sees the promotion and repairs the workspace head idempotently. That repair is the only automatic repair the store performs, and it is derived purely from a commit point.

Other workspaces forked from the old base can no longer promote.

Promotion never consults evaluation data.

### Loading (D5)
- Every snapshot read is parsed with `ProjectIRSchema`, and `hashProjectIR` must equal its filename hash.
- Every head and receipt is schema-validated, and its references must exist.
- Any mismatch, missing file or invalid JSON yields `store_corrupt` and fails closed: no repair, no fallback.

## Decisions requiring approval

| ID | Decision | Why |
| --- | --- | --- |
| D1 | Add one pure Core export, `checkProjectState(project, safety): { ok: true, contentHash } \| KernelFailure`. It parses both inputs, requires a matching project ID and checks genuine locks using the existing `checkLocks`. No new behavior. | The kernel rejects empty batches (`OperationsSchema.min(1)`), so promotion and init cannot reuse `applyBatch` to re-check state. This is the only Core change. |
| D2 | Add `'frozen'` to the workspace `state` enum. | Freezing a submission must block further edits without implying promotion. |
| D3 | `projectId` and `workspaceId` must be lowercase `[a-z0-9-]`, 1–64 chars, not a Windows reserved device name. Agent-supplied `batchId`s never become paths: deduplication lives in `head.json`, and receipt files are named by a hash-derived `receiptId`. | Core `IdSchema` accepts `../x`, `CON`, `abc.` and case variants. On Windows these alias or escape paths. Lowercase-only removes case collisions. Hash naming removes the agent-controlled path surface entirely. |
| D9 | Single commit point per scope: `head.json` per workspace, `accepted-head.json` per project. Deduplication, freeze and promotion read state only from commit points. Promotion's workspace `committed` state is derived from `accepted-head.promotions`. | Prevents false-success deduplication after a crash, and partially applied promotion or freeze. |
| D4 | Single-writer guard: `owner.lock` is created with exclusive-create (`wx`) holding `{ pid, startedAt }` and removed on clean close. A stale lock needs explicit manual removal; there is no automatic stealing. | The parent plan supports one sequential owner. This turns accidental double-opening into an error instead of silent corruption. It is not a distributed lock. |
| D5 | Hash-verify every snapshot on load. | Fail-closed corruption detection, as the parent plan requires. Costs CPU on large projects, which is acceptable for V0 fixtures. |
| D6 | Notes limit of 16 KiB, with their own revision counter. | Gives the bounded tool size Proposal 001 needs. The value is provisional and can be tuned in M5 identically for all arms. |
| D7 | Inject I/O through a small `StoreFs` interface (`readFile`, `writeFileAtomic`, `appendLine`, `exists`, `mkdir`, `createExclusive`, `remove`). It has a Node implementation and a test wrapper that can fail after N writes. | Interruption tests need deterministic fault injection, and production code stays plain `node:fs`. |
| D8 | On Windows, `rename` over an existing file can fail transiently (`EPERM`/`EBUSY` from antivirus or indexers). `writeFileAtomic` retries a bounded number of times (5 tries, short fixed backoff), then fails with a typed error. | The repo is developed on Windows 11. The retry is bounded and deterministic, and it never falls back to a non-atomic write. |

There are no new dependencies. The store uses only Node built-ins (`node:fs`, `node:path`, `node:crypto`) plus existing Zod and Core.

## Acceptance tests (deterministic, no media, no models)

Tests use temporary directories under the OS temp dir and synthetic fixtures from Milestone 2.

1. **Isolation.** Edits, undo, discard and notes in workspace A leave the accepted head and workspace B byte-identical.
2. **Apply.** A success bumps the revision by 1 and writes the receipt and snapshot; the head hash equals the kernel's `afterContentHash`.
3. **Stale revision, wrong workspace, non-open state.** Typed error, and no file changes besides the attempt line.
4. **Kernel failure.** A batch failing at operation N leaves the head and history unchanged, records the attempt, and passes the kernel error code through.
5. **Deduplication.**
   - An identical retry returns the original receipt with `replayed: true` plus the current head, and applies nothing twice.
   - Apply, undo, then retry: the old receipt comes back and the reported current head reflects the undo.
   - Same `batchId` with a different payload gives `batch_id_conflict`.
   - A retry after restart (fresh store instance) is still deduplicated.
6. **No-change batch.** Revision and stacks unchanged; deduplicated on retry; not undoable.
7. **Undo/redo.** Exact content-hash restoration with increasing revisions. A new edit clears the redo stack. Empty stacks give typed errors. Undo restores only stored, verified snapshots.
8. **Replay.** Matches every receipt. A tampered receipt or snapshot is detected (`replay` reports the mismatch, or loading gives `store_corrupt`).
9. **Promotion.** Succeeds from an unchanged base. Fails with `stale_base` after another workspace promotes. Fails on an empty timeline. A lock violation detected by D1 fails.
10. **Freeze and discard.** All later mutations fail; reads still work; `head.submission` binds the frozen revision, hash and notes revision.
11. **Corruption.** Missing snapshot, invalid JSON, a snapshot whose content does not match its hash, or a dangling receipt reference: each gives `store_corrupt`, with no partial load.
12. **Interruption.** This covers every write position *k* in apply (changed and no-change), undo, redo, freeze, promote and notes. The fault wrapper fails the *k*-th write, then a fresh store instance must:
    - load either the complete old state or the complete new state, never a mix, with orphans ignored;
    - on **retrying the same batch**, either apply it fresh (the earlier attempt was not committed) or return its receipt with `replayed: true` (only if `head.committedBatches` lists it), never a false success;
    - after a promote crash between commit and follow-up, report the workspace as `committed` and the accepted head as promoted.
13. **Safety binding.** Changing `safety.json` after a fork makes edits fail with `safety_changed`.
14. **Owner lock.** A second owner on the same project gets `owner_locked`. After a clean close, re-opening works.
15. **Path safety.**
    - Project and workspace IDs such as `..`, `a/b`, `a\b`, `C:x`, `abc.`, `Abc`, `con`, `NUL`, `com1`, empty strings and IDs over 64 characters are rejected before any filesystem access.
    - Batch IDs containing path characters (`../x`, `a\b`, `CON`) are accepted as data and never touch path construction.
16. **Notes.** Writing and reading round-trips exactly. A stale notes revision fails. Text over 16 KiB fails. Notes never change the content hash or workspace revision.
17. **Randomized history.** Fixed seed `0xAE7103`, 200 steps mixing apply, invalid apply, retry, undo, redo and notes. After each step, loading a fresh instance equals the in-memory model and replay passes. On failure, report the seed and journal.
18. **Boundaries.** The import-closure tests above pass, and the existing 93 tests still pass.

## Risks

- **Windows rename semantics** (D8). Mitigated by the bounded retry. Interruption tests run on the developer's Windows machine as well as on Ubuntu CI.
- **Full-snapshot disk use.** Accepted by the parent plan for small fixtures; compaction is deferred.
- **Owner-lock staleness after a crash** needs manual removal. This is documented, and it is safer than auto-stealing.
- **Scope creep into M4/M5.** Notes *storage* is included because it is workspace state. Notes *tools*, artifacts and previews are explicitly excluded.

## Implementation record — 2026-10-14

Approved by the owner on 2026-10-14 ("approve M3"). Implemented by the lead agent on branch `m3-workspace`. Packets WS-01 to WS-03 were not delegated; the lead implemented them directly.

**What was built**
- Core D1: `checkProjectState(project, safety)` in `packages/core/src/kernel.ts`. Pure; it passes the existing Core purity test. No other Core change.
- `@aether/workspace`:
  - `schemas.ts`: `StoreSegmentSchema`, `WorkspaceHeadSchema`, `AcceptedHeadSchema`, `BatchReceiptSchema`, `AttemptRecordSchema`, `NotesSchema` and the `WorkspaceError` type. `'frozen'` was added to `AgentWorkspaceSchema` (D2).
  - `fs.ts`: the `StoreFs` interface and `nodeStoreFs` (temp-then-rename, D8 retry of 5 tries with a 25 ms backoff, exclusive create).
  - `store.ts`: `initProject`, `openProjectStore` and a `ProjectStore` with fork, read, apply, undo, redo, replay, notes, discard, freeze, promote and close.
- New package dependency: `@aether/workspace` → `@aether/tools` (workspace protocol, for `TaskInstructionsSchema`). The lockfile changed by three lines. No external dependency was added.

**Deviations from the plan, all additive**
1. **Extra `WorkspaceError` codes.**
   - `already_exists`: init of an existing project, or fork of an existing workspace.
   - `project_not_found`: opening a project that doesn't exist.
   - `empty_timeline`: promotion of a timeline with no clips.
   - `invalid_input`: an invalid task at fork, or notes that are not text.
   - `io_failed`: filesystem failure, including D8 exhaustion.
   - The plan required each of these behaviours but named no code for them.
2. **Unknown workspace** gives `workspace_mismatch`.
3. **Stored IDs are re-checked before path use.** Receipt IDs read from `head.json` must match `receipt-<sha256>`, and promoted workspace IDs must pass `StoreSegmentSchema`. Otherwise the result is `store_corrupt`. This hardens D3 against tampered store files.
4. **Store state is not cached.** Every command reloads and re-verifies its commit points and snapshots. This is simple and correct for V0 sizes.
5. **Notes stale revision** uses `stale_revision`.
6. **`discard` and `freezeSubmission` require state `open`.** A frozen submission cannot later be discarded.
7. **Attempt lines are recorded only once the target workspace has loaded.** For example, a schema-invalid batch has no workspace to attribute.
8. **Receipt `clipMappings` are validated in place, not rebuilt.** Re-parsing with `z.record` dropped opaque keys such as `__proto__`, breaking the Milestone 2 promise that such IDs are mapped safely. A regression test now covers apply, stored receipt, deduplication and replay with a `__proto__` clip ID.
9. **Fault model for the interruption tests.** The fault wrapper (`tests/workspace-support.ts`) counts `writeFileAtomic`, `appendLine`, `mkdir`, `createExclusive` and `remove`.
   - A failing atomic write leaves a temp file but no rename.
   - After the fault, every later write fails, like a dead process.
   - Recovery follows D4: remove `owner.lock` manually, then reopen.

**Tests:** 31 new tests (93 → 124 total).
- `tests/workspace.test.ts` covers groups 1–11 and 13–16, D1, fork, the WorkspaceHead invariant and stored-ID hardening.
- `tests/workspace-history.test.ts` covers group 12 for apply (changed and no-change), undo, redo, freeze, promote, notes and discard at every write position. It also covers group 17 (seed `0xAE7103`, 200 steps, an independent model, a fresh owner instance and replay after every step).
- `tests/boundaries.test.ts` gains the workspace import-closure and no-`evaluations` check (group 18).
